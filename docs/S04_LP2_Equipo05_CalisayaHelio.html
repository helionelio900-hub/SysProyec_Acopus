Bloque 1: Modelo Cabecera-Detalle y Cálculos (Peso: 25%)

Se modeló la operación cabecera-detalle mediante la entidad principal LiquidacionG1 y su colección de líneas DetalleLiquidacionG1 con @OneToMany(mappedBy = "liquidacionG1", cascade = CascadeType.ALL, orphanRemoval = true). Cada detalle almacena el peso en gramos, precio por gramo derivado de la cotización internacional en tiempo de ejecución y el subtotal calculado.

// LiquidacionG1.java (Cabecera)
@Entity
@Table(name = "LIQUIDACIONES_G1", schema = "BOM_ACOPIO")
public class LiquidacionG1 {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long idLiquidacionG1;
    private String nombreAcopiadorG2;
    @Enumerated(EnumType.STRING)
    private EstadoLiquidacion estado = EstadoLiquidacion.REGISTRADA;
    private BigDecimal cotizacionOnzaUsd;
    private BigDecimal tipoCambioUsdPen;
    private BigDecimal pesoTotalFundidoG;
    private BigDecimal totalPagadoG2Pen;
    @OneToMany(mappedBy = "liquidacionG1", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<DetalleLiquidacionG1> detalles = new ArrayList<>();
}

Bloque 2: Regla de Negocio Real y Excepción de Conflicto 409 (Peso: 25%)

A diferencia de validaciones de formato, la regla de disponibilidad de inventario requiere consultar el balance real de oro en tiempo de ejecución. Si se solicita liquidar más gramos de los disponibles en el centro de acopio, AcopiadorService arroja StockInsuficienteException, la cual es transformada en HTTP 409 Conflict por GlobalExceptionHandler.

// GlobalExceptionHandler.java
@ExceptionHandler(StockInsuficienteException.class)
public ResponseEntity<Map<String, Object>> handleStockInsuficiente(StockInsuficienteException ex) {
    Map<String, Object> body = new HashMap<>();
    body.put("timestamp", Instant.now().toString());
    body.put("status", HttpStatus.CONFLICT.value());
    body.put("error", "Conflict");
    body.put("message", ex.getMessage());
    return ResponseEntity.status(HttpStatus.CONFLICT).body(body);
}

Bloque 3: Transacción Atómica, Commit y Caso de Rollback (Peso: 25%)

La operación procesarLiquidacionSemanal está anotada con @Transactional. Se demostró:

  • Caso Éxito (HTTP 201 Created): Con stock suficiente en todas las líneas, se persisten cabecera y detalles de forma atómica calculando subtotales y total exactos.
  • Caso Rollback (HTTP 409 Conflict): Cuando una línea solicita más stock del disponible, se interrumpe el flujo y Spring ejecuta un ROLLBACK total: ni la cabecera ni los detalles se persisten, y el stock de las líneas previas queda intacto.

3. ERROR O HALLAZGO TÉCNICO DIAGNOSTICADO

Hallazgo: Conflicto de Tipo de Excepción en la Propagación Transaccional de Spring @Transactional.

Diagnóstico: Si la excepción de regla de negocio hubiese extendido de Exception (checked exception) en lugar de RuntimeException (unchecked), el proxy transaccional de Spring por defecto no habría ejecutado el rollback, provocando commits parciales e inconsistencias contables.

Solución: Se definió StockInsuficienteException extends RuntimeException, garantizando que el rollback automático ocurra sin necesidad de parametrización manual propensa a fallos.

4. REFLEXIÓN TÉCNICA BREVE

¿Por qué una regla como "hay stock suficiente" no se puede expresar con Bean Validation, y qué capa sí puede validarla?

Una regla como "hay stock suficiente" no se puede validar con Bean Validation (como @NotNull o @Positive) porque Bean Validation únicamente inspecciona la forma sintáctica y la estructura intrínseca del DTO recibido en memoria de manera estática y aislada. La disponibilidad de inventario o stock no depende del formato del dato, sino del estado actual y concurrente del almacenamiento en base de datos. Por este motivo, la única capa competente para validar esta regla es la capa de Servicio (@Service), la cual interactúa con el repositorio, evalúa las existencias en tiempo de ejecución bajo una transacción @Transactional y lanza excepciones de negocio controladas.
