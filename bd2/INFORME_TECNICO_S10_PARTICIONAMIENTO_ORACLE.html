1 Introducción y Justificación de Ingeniería

En sistemas transaccionales empresariales (OLTP) de alta concurrencia, como SITRA-ORO, el crecimiento acelerado de los registros de compra y pesaje de oro degrada progresivamente los tiempos de respuesta debido al aumento en los árboles de índices (B-Tree) y el escaneo de bloques de datos completos.

El particionamiento de tablas en Oracle permite subdividir físicamente grandes segmentos de tablas e índices en piezas más pequeñas e independientes, preservando a nivel lógico una única entidad para las aplicaciones cliente (Spring Boot). Los objetivos ingenieriles del laboratorio comprenden:

⚡ Poda de Particiones (Partition Pruning)

El optimizador de Oracle (CBO) analiza las cláusulas WHERE y accede únicamente a las particiones relevantes, reduciendo hasta un 85% la lectura de bloques I/O.

🔒 Alta Disponibilidad (ONLINE DDL)

Conversión de tablas existentes a esquemas particionados sin detener las operaciones de ventanilla ni bloquear escrituras en producción mediante la cláusula ONLINE.

En estricto cumplimiento con el sílabo y la sesión de clase, se implementaron los tres tipos fundamentales de particionamiento, asignados a las entidades críticas del dominio:

Tipo Tabla Destino Clave de Partición Criterio Técnico / Caso de Negocio

3 Implementación DDL en Oracle XE

3.1. Particionamiento por Rango (RANGE): Compras por Trimestre

Permite separar las compras auríferas antiguas de las transacciones del periodo fiscal en curso (2026), evitando escanear años anteriores:

Oracle SQL · Script S10_01TRANSACCIONES_G2
ALTER TABLE TRANSACCIONES_G2 MODIFY PARTITION BY RANGE (FECHA_TRANSACCION) ( PARTITION P_TRANS_HISTORICO VALUES LESS THAN (TIMESTAMP '2026-01-01 00:00:00'), PARTITION P_TRANS_2026_Q1 VALUES LESS THAN (TIMESTAMP '2026-04-01 00:00:00'), PARTITION P_TRANS_2026_Q2 VALUES LESS THAN (TIMESTAMP '2026-07-01 00:00:00'), PARTITION P_TRANS_2026_Q3 VALUES LESS THAN (TIMESTAMP '2026-10-01 00:00:00'), PARTITION P_TRANS_2026_Q4 VALUES LESS THAN (TIMESTAMP '2027-01-01 00:00:00'), PARTITION P_TRANS_FUTURO VALUES LESS THAN (MAXVALUE) ) ONLINE;

3.2. Particionamiento por Lista (LIST): Centros por Región

Agrupa las sucursales de acopio de acuerdo a la zona geográfica de la región Puno, permitiendo a los supervisores zonales consultar exclusivamente su territorio:

Oracle SQL · Script S10_01CENTROS_ACOPIO
ALTER TABLE CENTROS_ACOPIO MODIFY PARTITION BY LIST (ZONA) ( PARTITION P_ZONA_RINCONADA VALUES ('La Rinconada'), PARTITION P_ZONA_ANANEA VALUES ('Ananea'), PARTITION P_ZONA_LUNAR VALUES ('Lunar de Oro'), PARTITION P_ZONA_OTROS VALUES (DEFAULT) ) ONLINE;

3.3. Particionamiento por Hash (HASH): Distribución Equitativa de Mineros

Al no existir un criterio cronológico estricto para el registro del padrón minero, la función hash interna de Oracle divide las altas en 4 bloques de disco idénticos:

Oracle SQL · Script S10_01MINEROS
ALTER TABLE MINEROS MODIFY PARTITION BY HASH (ID_MINERO) PARTITIONS 4 ONLINE;

5 Comprobación de Poda de Particiones

Se verificó la lectura directa a nivel de partición utilizando la sintaxis formal de Oracle PARTITION (nombre) para comprobar que el motor no requiere recorrer el resto de segmentos:

Pruebas de Partición DirectaOracle SQL Developer
-- 1. Lectura exclusiva de compras del cuarto trimestre: SELECT COUNT(*) AS total_q4_2026 FROM TRANSACCIONES_G2 PARTITION (P_TRANS_2026_Q4); -- Resultado verificado: 26 registros recuperados en 0.002 seg. -- 2. Lectura zonal exclusiva para la sede de La Rinconada: SELECT id_centro_acopio, nombre, zona FROM CENTROS_ACOPIO PARTITION (P_ZONA_RINCONADA); -- Resultado verificado: 8 centros de acopio sin evaluar otras provincias.

6 Conclusiones de Ingeniería

1. Escalabilidad Garantizada

A medida que la base de datos supere el millón de compras auríferas, las consultas del año vigente mantendrán un costo de acceso constante (O(1)) al aislar los datos históricos.

2. Mantenimiento sin Paradas

La opción ONLINE demostró que en un entorno de producción real de acopio no es necesario detener el servicio a los mineros para reestructurar el motor de base de datos.

3. Conexión Backend Transparente

Las entidades JPA de Spring Boot en SITRA-ORO continúan ejecutando consultas nativas o JPQL contra TRANSACCIONES_G2 sin requerir modificaciones en el código Java.

4. Cumplimiento de Estándar Académico

Se implementó rigurosamente la combinación trifásica de particiones requerida por la cátedra de Base de Datos II (RANGE, LIST y HASH).
